Accessibility

How WidgetCore meets accessibility requirements — the combobox pattern, ARIA roles, live regions, working without JavaScript, FAQ semantics, reduced motion, contrast and an audit checklist.

Last updated 2026-09-29

Accessibility in this plugin is not an extra layer: the markup, the keyboard behaviour and the ARIA attributes are built into every widget from the start. This page explains what is already handled and what you should check when you customise the output.

Live Search widget

The combobox pattern

The field follows the WAI-ARIA combobox pattern:

ElementAttributeMeaning
The inputrole="combobox"Announced as a combined field and list
The inputaria-expanded="true/false"Whether the results panel is open
The inputaria-controls="…-list"The id of the results list
The inputaria-autocomplete="list"Suggestions come from a list
The inputaria-activedescendant="…"The currently highlighted result
The results listrole="listbox"A selectable list
Each resultrole="option"A selectable item
The selected resultaria-selected="true"The highlighted option

Label and accessible name

Every field has an accessible name: a visible <label> when there is room, otherwise aria-label. The panel has aria-label too, and the results list is associated with the field through aria-controls.

Do not remove the label

If you restyle the field and hide the label with display: none, replace it with an accessible alternative such as aria-label or a visually-hidden label class. A missing label is the most common accessibility failure in custom search fields.

Live regions

Two live regions keep screen readers informed without stealing focus:

Regionaria-liveAnnounces
The status textpolite“8 results found.”, “No results found.”
The end-of-results messagepolite via role="status"No more results

The results list itself is not a live region: announcing every list change would be noisy, so only the count is announced.

Working without JavaScript

The markup contains a real <form> that submits with GET to the site root:

This is a simplified form example; the widget has no separate submit button. Without JavaScript, Enter in the input still submits and the visitor lands on the theme's native search results page. This means the widget never becomes a dead end for assistive technology or for a visitor with scripts disabled.

Closed state and focus

A closed answer is not merely visually hidden — it also leaves the tab order:

Using visibility (rather than only max-height) guarantees that links inside a closed answer cannot receive focus, so keyboard users never tab into invisible content.

Structured data

With the “FAQ schema” control on, the widget prints FAQPage JSON-LD. Two rules keep it valid:

  • Only items with both a question and an answer are included. Only the first rendered FAQ instance with schema enabled reaches schema generation. Instances with schema disabled do not consume this opportunity. Within that first enabled instance, only non-empty question/answer pairs are included; if none qualify, no block is printed and later instances still cannot emit one. This is the plugin’s one-block policy, not a claim that multiple FAQ blocks always cause a search-engine error. Valid JSON-LD does not guarantee a rich result; search-engine eligibility and content policies also apply.

Check the rich results

After publishing, test the page URL in Google's Rich Results Test. A valid FAQPage should be reported with each question and answer.

Without JavaScript

FAQ interaction requires JavaScript; there is no details/summary fallback. Closed answers remain hidden (max-height: 0). Only initially open answers remain visible, with a 640px CSS cap, so long answers can be clipped. Provide essential information outside the accordion when no-script access is required.

The widget needs no JavaScript of its own. Reply links use WordPress' own comment-reply script, which moves the form under the comment and back.

Reduced motion

All widgets respect prefers-reduced-motion:

WidgetWith reduced motion
FAQItems open and close instantly; the icon does not rotate with a transition
Live SearchThe panel appears without a fade; infinite scroll still works

The behaviour stays complete — only the animation is removed. Nothing is hidden or disabled.

Color contrast

The default palette was chosen for readable contrast:

PairRatioLevel
Result title (#0f172a) on whiteAbove 15:1AAA
Excerpt (#64748b) on whiteAbout 4.8:1AA
Placeholder (#94a3b8) on whiteAbout 2.6:1Below AA for normal text
FAQ question (#1F2937) on the cardAbove 13:1AAA
FAQ answer (#6B7280) on the cardAbout 5.0:1AA

Check placeholder contrast

Placeholder text is not exempt from contrast requirements. Darken it to meet 4.5:1 for normal text, and do not rely on it as the only instruction. Keep an accessible label so the purpose remains clear after typing starts.

Focus styles vary by control and state. Check focus visibility and contrast against the actual page background; the default palette alone is not a guarantee of compliance.

Text direction and layout

All layout rules use logical properties, so right-to-left and left-to-right both work from the same stylesheet:

Logical propertyInstead of
inset-inline-start / inset-inline-endleft / right
margin-inline / padding-inlinemargin-left / padding-right
border-inline-startborder-left
text-align: starttext-align: left

The icon position, the panel alignment and the pagination order therefore flip correctly on an RTL site without a second stylesheet.

Markup when customising

If you build a custom Elementor template for results, keep these attributes:

KeepWhy
role="option" on each resultSo aria-activedescendant keeps working
Meaningful links inside the templateTab and Enter activate each link normally
Text alternatives for imagesA meaningful alt, or alt="" when decorative
The heading level of the titleSo the results fit the page outline

The plugin wraps whatever your template prints, so the list roles stay intact; the input’s active-result navigation uses the result permalink even if the template has no link.

Publishing checklist

  1. Test with the keyboard only

    Tab through the field, open results with ArrowDown and Enter, close with Escape.

  2. Test with a screen reader

    Check that the field name, the result count and the FAQ state are announced.

  3. Test without JavaScript

    The search form must still submit. FAQ closed answers cannot open without JavaScript; only initially open answers remain visible, capped at 640px. Provide another way to read essential content.

  4. Check contrast

    Every text pair you changed should meet at least 4.5:1.

  5. Check reduced motion

    Enable the OS setting and confirm nothing animates.

  6. Validate the schema

    Run the page through the Rich Results Test.
